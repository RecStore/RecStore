### 索引

- PET 哈希把一个桶定为 14 个槽，每个槽附带 1 字节标签。标签取自哈希值的高位，桶下标取自低位，因此一次哈希计算同时给出「在哪个桶」和「和哪些标签比」。查找时，一条 SIMD 指令并行比较 14 个标签（`_mm_cmpeq_epi8`16字节），只有标签相等的槽才需要读出完整的 64 位 key 逐字节核对。多数不匹配的槽在这一步就被排除，省去了逐槽读 key 的开销。  
    批量读取时，引擎在处理当前 key 之前先预取下一个 key 的桶，让访存和计算重叠，这在随机读的负载下能显著减少停顿。
    
- 可扩展哈希用 16 槽的块和一份可翻倍的目录。目录按 key 的低位索引到块，块满时分裂成两个块，目录对应项随之更新。它的目录很小，扩展过程平滑，代价是分裂会在两个新块之间均分原来的槽，留下两个半满的块。连续插入后，块的平均填充率大致只有一半，因此每键占用的索引空间升到约 78 字节，高于 PET 哈希。
    

### 值存储与分配器

值存储处理的是变长字节块。同一个引擎里，不同 key 的 value 长度可以不同，分配器既要为每种长度找到合适的位置。

#### DRAM

内存值存储把一块连续的进程地址空间当作值区，句柄就是槽在值区内的字节偏移加一；偏移 0 保留给句柄 0，表示未命中。值区按 1 MiB 切成 chunk，每个 chunk 第一次使用时绑定一个尺寸档，档位是 32、64、128、512、1024 字节的载荷，槽大小是载荷加 8 字节长度头。例如一个 chunk 绑定到 128 档之后，被切成 7680 个 136 字节的槽。

例如写入一条 100 字节的 value：

- 取首个不小于它的档，100 落在 128 档，占用一个 136 字节的槽，8 字节头写入长度 100，后面 128 字节里前 100 字节是数据，槽尾 28 字节空闲。例如放到了 `0x00123420`。
    
- 每个 chunk 用一个 64 位字位图标记槽的占用，回收只需把对应的一位清零。线程各自缓存一个热 chunk，连续分配落在同一 chunk 内，减少对全局空闲结构的争用。
    

现在要读取这个value，获取了对应的句柄 `0x00123421`，根据上面规则算出偏移，可以读出 100 字节。这时候值在内存里，读可以先返回指向槽的零拷贝视图，值区也能注册给 RDMA，让远端直接读同一段地址。

#### SSD

固态盘值存储同样会根据相同的尺寸档，句柄会拆成两部分：高 16 位是档位序号，低 48 位是介质内的槽序号。槽序号再按块号与块内槽号拆开，折算成字节偏移（=块号*每块槽数+块内槽号）。

值区按 64 MiB 切块，槽按尺寸档紧密排列。128 档的槽是 4 字节长度头加 128 字节载荷，共 132 字节，因此每块能放下 floor(64 MiB / 132) = 508400 个槽。

例如对于写入一条单键 value：读入槽所在页，写入 4 字节长度头和数据，整页写回。批量写把落在同一页的多个补丁合并，整页只读写一次；批量读把多条记录一次提交，在途 IO 数由队列深度控制。

分配器有两种粒度：slab 把块切成等长槽，适合长度固定、写入密集的场景；buddy 把块按 2 的幂分裂与合并，适合长度差异大、需要向上取整的场景。

> 分配顺序决定物理位置。如果没有好的布局政策来将读取的嵌入共同存放，大规模 SSD 查找会支付大量随机页面读取。以往的系统表明，访问感知的共置可以显著提升 SSD/NVM 的有效带宽——例如 [Bandana](https://proceedings.mlsys.org/paper_files/paper/2019/hash/d59a1dc497cf2773637256f50f492723-Abstract.html)（超图分区+DRAM 缓存大小）和 [MaxEmbed](https://github.com/Ksitta/MaxEmbed)（分区+复制用于 SSD 页面打包）。RecStore 后续会将这些布局机制纳入可选策略，通过捕捉共现关系来进行加速，并可替换为 SSD 服务/混合层级。

### IO 后端（SSD）

SSD 相关的操作都是以 4 KiB 一页为单位进行操作，包括同步与异步读写、脏页回写、批量读写，以及提交与完成收割。值存储和页号分配都通过固定的接口访问物理盘。

- io_uring 后端把值区当作一个普通的直接 IO 文件：打开时带上 O_DIRECT，读写绕过内核页缓存，每次搬运一整页。每个线程持有自己的 io_uring 实例，队列深度取自配置，默认 512。单键读写的流程是把请求写进提交队列，提交并等待，再从完成队列取出结果。异步路径把 io_uring 与协程绑定：提交后挂起协程，该请求的完成事件到达时恢复它。  
    批量路径使用滑动窗口，在途请求上限为队列深度的一半。一个请求可以覆盖多页连续区间，因此窗口内的页数通常大于请求数。每轮提交之后轮询完成队列，回收一个就补交一个，使窗口始终填满。
    
- SPDK 后端绕过内核，直接在用户态驱动 NVMe 设备。初始化时按固定的 PCIe 地址探测控制器并选取一个活跃命名空间，此后设备归进程独占，文件系统不再参与。每个线程持有一个 queue pair，深度同样取自配置。读写请求在调用时直接提交，不产生系统调用；完成情况由线程主动轮询队列获得。由于绕过了内核，IO 缓冲必须来自支持 DMA 的内存池，而不是普通堆内存，这样就有更短的单次 IO 路径。  
    代价是设备地址与构建开关要在部署时确定，设备需要从文件系统上卸载并交给进程独占。
